# The Baa website

A static site. No Node, no PHP, no database, no build step on the server:
upload the files and it works.

Live at [sheep.grimtech.co.uk](https://sheep.grimtech.co.uk).

---

## Building it

```bash
npm run gen:playground   # compile the interpreter for the browser
npm run gen:site         # build the HTML from the repository's Markdown
node tools/check-site.ts # verify: no broken links, no missing anchors
```

Or all of it, together with the generated docs and the conformance suite:

```bash
npm run gen
```

## Deploying to cPanel (or any shared host)

1. Run `npm run gen` locally.
2. Upload the **contents** of `website/` into `public_html`.
3. That is the whole procedure.

Everything is relative-path linked, so it also works from a subdirectory:
`public_html/baa/` serves correctly at `example.com/baa/` with no
configuration change.

The included `.htaccess` is optional polish, not a requirement:

- pretty URLs (`/docs/language` serves `docs/language.html`);
- sensible cache headers and gzip;
- `X-Content-Type-Options`, `Referrer-Policy` and a Content-Security-Policy
  that allows nothing from any other origin;
- a `404.html` error page.

Every block is wrapped in `<IfModule>`, so the site still serves correctly if
the host has a module disabled. If your host ignores `.htaccess` entirely,
delete it: nothing breaks, you simply lose the pretty URLs.

The site needs no PHP. If your host only serves `index.php`, a one-line
`index.php` containing `<?php readfile('index.html');` works, but on every
cPanel account tested `index.html` is already in `DirectoryIndex`.

### Other hosts

| Host | What to do |
| --- | --- |
| GitHub Pages | Publish the `website/` directory. Everything is relative. |
| Netlify / Vercel | Build command `npm run gen`, publish directory `website`. |
| S3 / Cloudflare / any CDN | Sync `website/`, set `index.html` as the index document and `404.html` as the error document. |
| A folder on your laptop | `npx serve website`, or open `index.html` directly; only the playground needs a server, because module workers are not allowed from `file://`. |

## What is generated, and what is hand-written

Generated by `tools/build-site.ts`: do not edit these, they are overwritten:

```
index.html          playground.html          404.html
docs/*.html         docs/search-index.json   sitemap.xml
```

Generated by `tools/build-playground.ts`:

```
assets/baa/**       the interpreter, compiled to browser JavaScript
```

Hand-written, and the actual sources:

```
src/index.body.html        the homepage
src/playground.body.html   the playground
src/404.body.html          the error page
src/docs.index.md          the documentation hub
assets/styles.css          all the styling
assets/site.js             theme, nav, copy buttons, tabs, search
assets/highlight.js        Baa syntax highlighting for static snippets
assets/playground.js       the playground UI
assets/playground-worker.js  runs programs off the main thread
assets/shims/*.js          browser stand-ins for the node: builtins
assets/icon.svg            the mark
assets/logo.svg            the mark plus wordmark
assets/social.svg          the Open Graph card
.htaccess  robots.txt      server configuration
```

Every documentation page comes from Markdown that lives in the repository root
or in `docs/`, so the website cannot say something the repository does not.

## The playground

`assets/baa/` is the genuine Baa implementation, the same lexer, parser,
resolver, runtime and standard library the CLI uses, compiled from TypeScript
to ES modules by `tools/build-playground.ts`. It is not a re-implementation and
it is not a subset.

Two build details make that possible:

- TypeScript rewrites `./x.ts` import specifiers to `./x.js`, so the output
  loads in a browser with no bundler.
- The build then rewrites `node:path`, `node:fs`, `node:process`,
  `node:crypto` and `node:child_process` to the small shims in
  `assets/shims/`. That is done at build time rather than with an import map,
  because import maps do not apply inside a Web Worker: and the playground
  runs programs in a worker so an endless loop can be terminated.

`wool`, `flock`, `ram`, `meadow` and `lamb` work fully in the browser.
`pasture` and `shepherd` load, and report a clear Baa error when asked for a
file or a subprocess.

## Brand assets are public URLs

The repository README, and anything else that needs the logo, links these
directly rather than copying files:

    https://sheep.grimtech.co.uk/assets/icon.svg
    https://sheep.grimtech.co.uk/assets/logo.svg
    https://sheep.grimtech.co.uk/assets/social.svg

Absolute URLs because npm renders the README without the repository around it,
so relative image paths break there. A test asserts that every asset URL in the
README still resolves to a file in `assets/`, so renaming one fails CI rather
than silently breaking the images.

All three are plain SVG with no external references, so they work as `<img>`
sources anywhere, including on GitHub.

## Design notes

- **No web fonts, no CDN, no analytics, no cookies.** Everything is served from
  this origin, which is why the Content-Security-Policy can be as strict as it
  is.
- **Progressive.** With JavaScript disabled you lose syntax colours, the theme
  toggle, docs search and the playground. Every page is still complete and
  navigable.
- **Dark mode** follows the system by default and remembers an explicit choice.
  The theme is applied by a tiny inline script before first paint, so there is
  no flash of the wrong colours.
- **Reduced motion** is respected: `prefers-reduced-motion` turns off smooth
  scrolling and every transition.
- **Accessibility**: a skip link, one `<h1>` per page, landmark elements,
  visible focus rings, labelled controls, and `aria-current` on the active
  navigation item. `tools/check-site.ts` checks the structural parts on every
  build.
